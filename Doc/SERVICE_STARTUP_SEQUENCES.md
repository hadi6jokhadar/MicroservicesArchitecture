# Service Startup Sequences

Exact, ordered startup sequence for every service, read directly from each service's `Program.cs` (or `main.py` for AI). Use this to answer "what actually happens between process start and ready-to-serve" for any service, and to see at a glance which steps are blocking (delay startup) vs. which are background services that start at `app.Run()` (the highest-risk moment — see "Background-service risk" at the bottom).

**Last Updated:** August 10, 2026

**Legend:**
- `> **bold step**` — blocking (`await`ed before the middleware pipeline/`app.Run()`); a slow or unreachable dependency here delays startup.
- `> **bold step (background X starts here)**` — a registered `IHostedService`/`BackgroundService` actually starts running at this point (always at `app.Run()`), not when it was registered earlier in the file.

**Update (August 10, 2026):** the rate limiter middleware in Identity, FileManager, Category, and Notification moved from *before* authentication to *after* it. Their "PerUser" rate-limit policy partitions by the caller's `NameIdentifier` claim, which only exists once `UseAuthentication()` has populated `context.User` — running the limiter earlier meant every request evaluated to the same `"anonymous"` partition key regardless of who was actually calling, so "PerUser" was silently acting as one shared bucket for all traffic instead of a real per-user limit. "PerTenant" was never affected by this — it reads the raw `x-tenant-id` request header directly, not `ITenantContext`, so it works regardless of pipeline position. The sequences below already reflect the corrected order.

**Update (August 10, 2026):** `UseGlobalExceptionHandler()` moved to be the very first middleware in all nine .NET services. ASP.NET Core middleware wraps in registration order — earlier middleware's `try { await next(context); }` is what invokes later middleware, so it catches exceptions *from* later middleware, not the other way around. Two different orderings existed before this fix: Identity/Tenant/Notification/Translation/Backup had the handler positioned before compression/rate-limiter/HTTPS-redirect (so those three were already covered, but correlation-ID and localization — registered *before* the handler — were not); FileManager/Category/PolySnap/Nasheed had it positioned *after* HTTPS-redirect, compression, correlation-ID, and localization (so none of those four were covered — the more severe gap, since an unhandled exception there also had no correlation ID attached). Both are now the same, corrected shape: exception handler first, then correlation-ID, then localization, then everything else unchanged. The sequences below reflect the corrected order.

**Update (August 10, 2026):** `WarmUpCacheAsync()` in Identity and Tenant changed from a blocking `await` to fire-and-forget (`_ = app.Services.WarmUpCacheAsync();`). A cold Redis handshake was observed taking 11+ seconds under load — awaiting it just moved that delay from "first real request" (where callers have their own fail-fast timeouts) to "process startup" (where nothing was timing it out, so a slow Redis could stall the whole service indefinitely). The method has its own internal catch-all and can never throw, so discarding the task is safe. Both services' startup sequences below reflect this — the Redis warm-up step is no longer marked blocking.

## AI (port 5008 — Python/FastAPI, different model)

startup > module imports execute > init logging > set up OpenTelemetry tracing (best-effort) > quiet noisy third-party loggers > construct FastAPI app (lifespan handler registered, not yet run) > register exception handlers > add CORS middleware > wire OpenTelemetry + Prometheus `/metrics` (best-effort) > mount routers (settings, prompts, chat, sessions, messages, files, token-usage, embedding, transcription) > register `/health` (now runs `get_schema_health()` — reachability + Alembic-revision-vs-head check, `503` if stale/unreachable — see below) > `uvicorn.run(...)` starts the actual server process > **lifespan startup begins: ensure database exists** > **run Alembic migrations via blocking subprocess (failure is only logged, does NOT stop startup)** > **ensure schema exists** > lifespan `yield` (startup phase complete) > uvicorn binds the socket > **ready to use**

> **Fixed (August 10, 2026):** `/health` used to be a hardcoded `{"status": "healthy"}` with no DB check at all — combined with the migration-failure-is-only-logged step above and Gateway's `/health/aggregate` always calling `/health` (never a separate readiness endpoint, true for every service — see the note below), a failed AI migration would show green everywhere, forever. `/health` now calls `core/database.py`'s `get_schema_health()`, which compares the DB's `alembic_version` against the head revision resolved from `alembic/versions/` and returns `503` if they don't match or the DB is unreachable — matching what every .NET service's `/health` already does via `AddNpgSql`.

## Gateway (port 5000 — no database, pure reverse proxy)

startup > load config > load YARP reverse-proxy routes/clusters from config (this IS the downstream-routing setup — Identity, Tenant, etc.) > add request-timeout policies (per-route timeouts, e.g. AI streaming) > add named HTTP client for downstream health checks > read rate-limit settings from config > add rate limiter (global token-bucket limiter applied to every request by default, plus named "per-ip" and "health-aggregate" policies) > **build app** > inline middleware: overwrite `X-Correlation-Id` on every request (never trusts client-supplied value) > map `/health` (gateway-only, exempt from all rate limiting) > map `/health/aggregate` (fans out to every downstream service's `/health` in parallel) > activate rate-limiter middleware > if production: HSTS + HTTPS redirect > activate request-timeout middleware (must sit before the proxy or per-route timeouts throw) > map the actual reverse-proxy endpoint (per-ip rate limit applied) > **app.Run()** *(no database, no background services of any kind)* > **ready to use**

## Background-service risk, at a glance

Every `**bold**` step above marked "blocking" happens *before* `app.Run()` — a slow or unreachable dependency there just delays startup, it doesn't crash it (as long as the awaited call itself doesn't throw). Every step marked "background X starts here" happens *at* `app.Run()`, when the host starts every registered `IHostedService`/`BackgroundService` — this is exactly the moment where an unguarded exception can take the whole host down (see `TenantProvisioningListenerService`'s `ExecuteAsync` fix, `Dotnet.instructions.md`).

| Service | Hosted/background services started at `app.Run()` |
|---|---|
| Identity | Tenant-provisioning listener |
| Tenant | *(none)* |
| Notification | `NotificationProcessor` (unconditional) + tenant-provisioning listener + Hangfire's own processing |
| FileManager | Tenant-provisioning listener + Hangfire's own processing |
| Translation | *(none)* |
| Category | Tenant-provisioning listener + Hangfire's own processing (if Redis enabled) |
| AI | *(none — different model entirely; migrations run inline in the lifespan handler, not as a background service)* |
| **Nasheed** | **`NasheedTenantLoaderService` + `NasheedIngestionWorker` + tenant-provisioning listener + tenant-config-updated listener (if Redis enabled) — 4 at once, the highest exposure** |
| Backup | *(none — periodic work is Hangfire-scheduler-backed, not `IHostedService`)* |
| PolySnap | Tenant-provisioning listener |
| Gateway | *(none — no database, no hosted services)* |
